## Phase 16 accounting gap

- The architecture requires wage accrual to recognize wage expense plus wage payable exactly once, while payment only clears that existing obligation. The first scheduler implementation creates the obligation row at accrual but only journals the later cash transfer, so it does not yet satisfy T01 even though its cash postings balance.
- T01 also requires partial payment and later catch-up against the same obligation and an independent idempotent settlement record. The current one-shot payment leaves arrears but has no follow-up settlement task/table.
- T02/T03 require queryable arrears, rent rejection/grace evidence, and debt relationships without hidden overdraft. Existing obligation rows capture part of this, but Phase 16 needs explicit accrual accounts/settlements and executable assertions before the 90-day result can be accepted.
- The corrective accounting model will use four signed ledger accounts per contract: payer expense and payable plus recipient receivable and income. Accrual posts `expense + / payable - / receivable + / income -`; payment posts `payable + / payer cash - / recipient cash + / receivable -`. This keeps each journal balanced while separating expense recognition from cash settlement and making both sides of the debt replayable.
- A dedicated immutable settlement record is needed for each payment attempt so zero-payment failures, partial payments, retries, and catch-up payments remain queryable even when no cash posting occurs.
- Migration 003 intentionally stops at obligations and has no account mapping or settlement-attempt table; these belong in an additive migration 004 so the historical M0/002/003 contracts remain byte-stable.
- Replay folds every posted account seen in authority, including accounts that net back to zero; projection comparison ignores untouched zero-only projection rows but will validate every accrual account after its first posting. The four-account model therefore fits the existing replay/rebuild path without special replay rules.
- Paid store restocks provide a non-issuance enterprise revenue path: six traceable source restocks transfer 300 existing currency from the store to the enterprise. This enables two later 50-unit catch-up payments on the same employee-2 wage obligation while preserving arrears elsewhere.
- Current 90-day deterministic totals after catch-up are: 9 wage obligations with 1400 unpaid, 9 rent obligations with 450 unpaid, 22 successful and 14 rejected household purchases, 6 paid restocks, seller inventory 18, and branch head/event count 98 including genesis.
- Phase 16 now covers T01–T03 with executable evidence: duplicate accrual skips without duplicate expense; two catch-up settlements reference the same partial wage obligation; zero-fund wage/rent attempts commit structured failure evidence; rent grace transitions remain queryable; reverse task insertion does not alter the delinquency outcome; and food budgets are enforced before settlement.

## M2 T09 entry findings

- T09 is the first M2 backend slice: Cohort materialization/dematerialization must conserve population, assets, inventory, receivables, and liabilities and must not invent personal history.
- The slice is cross-cutting enough for the full-project route because it changes persisted state, authority events, idempotency, replay/snapshots, projection recovery, authorization, and transport.
- `vexor` semantic discovery failed again with an OpenAI connection error. No semantic results were used; continue with scoped local `rg` and direct file inspection.
- Existing replay already treats balanced postings and stock movements as the authoritative economic folds. T09 should reuse those facts for assets, receivables, liabilities, and inventory rather than introduce a parallel generic balance system; only population requires a new typed authority fact and replay projection.
- Migration 003's `economic_entities` CHECK has no `cohort`/generic `person` kind. The design must either use a separate Cohort/materialized-entity root or perform a risky table rebuild; an additive separate root is preferred until code inspection disproves it.
- Injecting Cohort seeds into the existing M1 `WorldInitialized` event would change historical counts/hashes and would not upgrade already-bootstrapped databases consistently. Prefer a separate M2 demo instance/branch and explicit `BootstrapM2Demo` path so M1 evidence remains byte/behavior stable.
- Safe dematerialization should require the named entity's materialized population/economic holdings to still equal the recorded allocation. If later activity changes them, reject instead of absorbing unrelated state into the aggregate.
- `accounts.owner_id` and `stock_locations.owner_id` are intentionally unconstrained text, so M2 can add separate `cohorts` and `materialized_entities` roots without rebuilding M1's `economic_entities` CHECK-constrained table.
- The materialization allocation maps to three account categories: asset and receivable balances transfer as positive values; liability transfers by moving a negative balance from Cohort to entity. All six postings net to zero in one currency. Inventory remains one ordinary transfer movement.
- Migration 006 should add `cohorts` (aggregate projection and economic bindings), `materialized_entities` (named projection and deterministic account/location bindings), `cohort_materializations` (immutable allocation/lineage plus lifecycle), and `population_movements` (authority facts).
- Replay can preserve old M1 snapshot hashes by adding population balances with `omitempty`; old snapshot payloads then canonicalize exactly as before, while M2 snapshots include nonempty population state.
- The isolated M2 genesis should use dedicated instance/branch, currency, SKU, accounts, and locations. One balanced opening journal, one inventory creation movement, and one population creation movement make its complete initial state replayable without changing M1 counts or hashes.
- Materialization identity and ordinary command idempotency are distinct: same command key/hash replays by the generic command ledger; a second command using an existing `materialization_id` replays only if its canonical request hash matches, otherwise it returns `MATERIALIZATION_ID_CONFLICT`.
- Dematerialization uses its own idempotent command. It must verify the lineage is active and every individual population/account/inventory projection still equals the recorded allocation before committing reverse facts; otherwise return `CONSERVATION_FAILED` with no writes.
- Phase 24 proves the selected authority shape works without a parallel resource ledger: one materialization event can own the balanced account transfers, stock transfer, population transfer, lineage, projections, audit, Outbox, and branch CAS atomically.
- Materialization command hashing intentionally excludes `command_id` and `idempotency_key`, matching existing command semantics. This lets both transport retries and a retried `materialization_id` return the original commit while preserving payload mismatch detection.
- Phase 25 proves dematerialization cannot silently absorb post-materialization changes: population, each account category, and inventory are independently checked against lineage before any command row is inserted.
- Population replay is optional in canonical snapshot JSON, so all pre-M2 M1 snapshots keep their old hash. M2 replay folds create/materialize/dematerialize movements and derives lifecycle status from owner kind plus replayed population.
- M2 demo initialization should remain explicit rather than run on every server startup. A thin `corerp-m2` CLI can seed the isolated fixture before the existing server opens the same database, avoiding hidden demo state in ordinary M1 operation.
- Multi-instance audit found `ReadDemoState` scoped balances but counted commands/events/facts across the entire database. Before sharing a database with the M2 fixture, all M1 counts must join/filter through the M1 instance and branch; otherwise an unrelated M2 event changes the M1 API response.
- Compiled-process evidence confirms the explicit bootstrap workflow works with the unchanged server lifecycle: seed M2 first, start the server on the same database (which may also bootstrap isolated M1), then use creator-scoped commands and ordinary visible-event queries.
- T09 is complete as a backend vertical slice, not as full M2. The next dependency-ordered backend increment is bounded Agent knowledge/schedules/encounters; scale and subjective status remain later gates.
